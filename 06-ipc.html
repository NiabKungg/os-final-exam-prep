บทที่ 6 — การสื่อสารระหว่าง Process: Signal, Pipe, Shared Memory

Process แยก address space ออกจากกันเด็ดขาด (เพราะบท memory) ถ้าอยากคุยกันต้องผ่าน "ช่องทางที่ OS จัดให้" 3 แบบหลักของ UNIX: Signal, Pipe และ Shared Memory

1. Process อิสระ vs ร่วมมือกัน

  • Independent — ไม่กระทบกันเลย
  • Cooperating — มีผลต่อกัน/แลกข้อมูลกัน เหตุผลที่ต้องร่วมมือ: แชร์ข้อมูล (information sharing), เพิ่มความเร็ว (computation speedup), แบ่งโมดูล (modularity)

แต่พออยากคุยกัน ต้องมี IPC (Interprocess Communication) — UNIX ให้มา 3 อย่าง: Signal · Pipe · Shared Memory (นอกนั้นยังมี message passing แนวคิดกว้าง ๆ)

2. Signal — "ตบไหล่" บอก process ให้หยุดฟังก่อน

Signal = software interrupt ที่แจ้ง process ว่า "มีเหตุการณ์เกิดขึ้นแล้ว!" ข้อมูลที่ส่งได้น้อยมาก (ส่งได้แค่หมายเลข signal) จึงใช้กับการแจ้งเตือนง่าย ๆ เช่น:

  • Error/exception — "หารศูนย์แล้วนะ!"
  • เหตุการณ์ภายนอก — "ผู้ใช้กด Ctrl+C!"
  • การแจ้งเตือน — "ลูกทำงานเสร็จแล้ว!", "หมดเวลาแล้ว!"

Signal ที่ต้องรู้จัก (จำพวก SIGKILL เป็นพิเศษ)

ชื่อเกิดเมื่อไรข้อสังเกต
SIGFPEคณิตศาสตร์พัง (หารศูนย์, overflow/underflow)FPE = Floating Point Exception
SIGINTกด Ctrl+CInterrupt — ขอให้โปรแกรมหยุด
SIGTERMขอ terminate แบบสุภาพ (ค่า default ของคำสั่ง kill)จับ/ปัดป้องได้
SIGQUITกด Ctrl+\non-ANSI C
SIGUSR1/2ให้โปรแกรมเมอร์กำหนดเองnon-ANSI C
SIGKILLสั่งฆ่าทันทีจับ (catch) หรือเมิน (ignore) ไม่ได้เด็ดขาด — โดนแล้วตายแน่ = kill -9

3 ทางเลือกของ process เมื่อรับ signal

  1. Catchกำหนดhandler function เอาไว้ทำงานเฉพาะเมื่อโดน signal นั้น
  2. ใช้ Default ของ OSไม่ตั้งอะไรเลย OS จัดการตามมาตรฐาน (ส่วนใหญ่คือ terminate)
  3. Mask (ปิดกั้น)บอก OS ว่า "signal ชนิดนี้ค้างไว้ก่อน (withhold) จนกว่าฉันจะเปิด mask ออก"

ฟังก์ชัน signal() — ติดตั้ง handler

signal_demo.c
signal(int signum, void (*handler)(int));
// ex. บอก OS ว่า: ถ้าเห็น SIGINT ให้เรียกฟังก์ชันชื่อ sig_handler
signal(SIGINT, sig_handler);

void sig_handler(int sig) {   // handler ต้องรับ int (เลข signal) คืน void
    printf("ไม่ยอมตายง่าย ๆ หรอก! (sig=%d)\n", sig);
}

ถ้าต้องจัดการหลาย signal มี 2 แนวทาง: ติดตั้ง handler แยกทีละตัว หรือ ใช้ handler เดียวรับหมดแล้ว switch (sig) แยกกรณีเอง

3. การส่ง Signal — raise(), kill(), คำสั่ง kill

เครื่องมือใช้ส่งให้ใครรูปแบบ
raise(sig)ส่งให้ตัวเอง (calling process)สำเร็จคืน 0, error คืนค่าไม่ใช่ศูนย์
kill(pid, sig)ส่งให้process อื่น (หรือกลุ่ม)สำเร็จคืน 0, error คืน -1
คำสั่ง kill ใน shellจาก command linekill -SIGNAL pid ... (ชื่อไม่ต้องมี SIG เช่น kill -INT 123)

ค่า pid ใน kill() — ออกเติมคำ/ถูกผิดบ่อย

ค่า pidความหมาย
> 0ส่งให้ process ที่มี PID ตรงตามนั้น
0ส่งให้ทุก process ในprocess group เดียวกับผู้เรียก
-1ส่งให้ทุก process ที่เรามีสิทธิ์ส่ง (ยกเว้น process 1 / init)
ค่าลบอื่นส่งให้ทุก process ที่ process group ID = |pid|
🎯 จุดหลอก

kill -9 pid = ส่ง SIGKILL — ตัวเดียวที่ process จับ/เมินไม่ได้ · ถ้าไม่ใส่ชื่อ signal คำสั่ง kill จะใช้ SIGTERM เป็นค่าเริ่มต้น (ไม่ใช่ SIGKILL!)

4. Message Passing และเรื่อง Blocking

แนวคิดแม่แบบของการคุยกัน: มี send(message) กับ receive(message) — ก่อนคุยกันต้องมี communication link ถ้าจะส่งสองทางใช้สองทางเดินข้อความ (ทิศทางละหนึ่ง)

Blocking send = Synchronous (ส่งแล้วรอจนถูกรับ) Blocking receive = รอจนมีข้อความ Non-blocking send = ส่งปุ๊บเดินปั๊บ (Asynchronous) Non-blocking receive = ได้ข้อความหรือ null

5. Pipe — ท่อส่งข้อมูลทางเดียว 🔥

Anonymous pipe = ท่อไบต์ทางเดียว (one-way) สร้างด้วย pipe(pfd) — OS ให้มาเป็นfile descriptor 2 ตัว: pfd[0] = ปลายอ่าน, pfd[1] = ปลายเขียน (จำ: 0 อ่าน, 1 เขียน — เหมือน stdin/stdout)

pipe.c (โครง)
int pfd[2];
pipe(pfd);                    // สร้างท่อ
write(pfd[1], buf, size);     // เขียนผ่านปลาย [1]
read(pfd[0], buf, SIZE);      // อ่านผ่านปลาย [0]

เมื่อ fork แล้ว ท่อจะโตขึ้นเป็น 4 ปลาย!

ประเด็นสำคัญที่วิดีโอเน้น: pipe() สร้างก่อน แล้วค่อย fork() — ลูกจะได้ copy ของ descriptor ทั้งคู่ → กลายเป็นมี 2 read end + 2 write end ทั้งสองฝั่งเขียน/อ่านได้ = รก! วิธีจัดการให้เป็นระบบ:

  1. ตกลงบทบาทให้ชัดเช่น parent = ผู้ส่ง, child = ผู้รับ
  2. Parent ปิด read endclose(pfd[0]) — พ่อเขียนอย่างเดียว
  3. Child ปิด write endclose(pfd[1]) — ลูกอ่านอย่างเดียว
  4. กลายเป็นสายพานเรียบร้อยข้อมูลไหลทางเดียว parent → child

ตัวอย่าง "ls | wc" — shell ทำได้ไง

เมื่อคุณพิมพ์ ls | wc shell จะ: สร้าง pipe → fork สองครั้ง → parent ตัวหนึ่ง exec เป็น ls (ผู้เขียน) อีกตัว exec เป็น wc (ผู้อ่าน) — ปัญหาคือ ls ปกติเขียนไปที่ fd 1 (stdout), wc ปกติอ่านจาก fd 0 (stdin) แต่ปลายท่อเราได้มาเป็น fd 3, fd 4 ทำยังไงให้เข้าที่? → ใช้ dup2()

6. dup2() — อยากให้ fd ตัวไหน "กลายเป็น" ตัวไหนก็ได้

dup2
dup2(fd, fd2);
// "fd อยากเป็น fd2" — ชี้ fd2 ไปที่ไฟล์/ท่อเดียวกับ fd แล้วปิด fd เดิมได้

// ตัวอย่าง: ปลายเขียนของท่อคือ fd=3, อยากให้กลายเป็น stdout (1)
dup2(3, 1);   // fd=1 ชี้มาที่ท่อแล้ว → ls พิมพ์ลงท่อโดยไม่รู้ตัว!
close(3);     // เก็บของ ปิดของเกิน

// ฝั่ง wc: ปลายอ่านคือ fd=4, อยากให้กลายเป็น stdin (0)
dup2(4, 0);
close(4);

dup2 มีประโยชน์ทั่วไป: redirect เช่น หัน stdout ไปเขียนลงไฟล์แทนจอ

📌 อยากคุยสองทาง?

pipe เป็นทางเดียว — ถ้า parent อยากทั้งเขียนและอ่านกับ child ต้องสร้างสองท่อ: ท่อแรก parent เขียน→child อ่าน, ท่อสอง child เขียน→parent อ่าน (ไฟล์ twopipe.c ในวิดีโอ)

7. Shared Memory — เปิดพื้นที่ RAM ให้แชร์กันตรง ๆ 🔥

แนวคิด: ให้ process สองตัว "ผูก" พื้นที่ RAM ก้อนเดียวกันเข้า address space ของตัวเอง แล้วอ่าน/เขียนกันเหมือน memory ของตัวเองเลย — เร็วที่สุดเพราะไม่ต้องผ่าน kernel ทุกครั้ง แต่ไม่มีการป้องกันให้! (ถ้าไม่จัด synchronization เอง จะเจอ race condition — ตัวต่อบท 7)

โปรโตคอลของ Server (ตัวตั้ง) และ Client (ตัวเข้าร่วม)

ขั้นSystem callทำอะไร
1shmget(key, size, flag)ขอ shared memory ด้วย key → ได้ shared memory ID (server ใช้ IPC_CREAT | 0666 = สร้าง+อนุญาตอ่านเขียน · client ใช้แค่ 0666)
2shmat(id, NULL, 0)Attach พื้นที่เข้า address space → คืน pointer (cast เอา) · flag SHM_RDONLY = อ่านอย่างเดียว
3ใช้งานเขียน/อ่านผ่าน pointer (server เริ่มก่อน และเตรียมพื้นที่ให้พร้อม)
4shmdt(ptr)Detach — เลิกใช้ (ยังไม่ถูกลบ ผูกกลับได้ อาจได้ address ใหม่)
5shmctl(id, IPC_RMID, NULL)ลบ shared memory ทิ้ง (อยากใช้อีกต้อง shmget ใหม่)

Key — บัตรเข้าใช้พื้นที่ มี 3 วิธีได้มา

  1. เลขกำหนดเองkey = 1234; — ง่ายแต่เสี่ยง: ใครใช้เลขเดียวกันก็ล้วงเข้ามาได้
  2. ftok()key_t ftok(const char *path, int id); — สร้าง key จาก path + id ตัวเลข (นิยมใช้ "." = directory ปัจจุบัน) — process ที่เรียกด้วย argument เหมือนกันจะได้ key เดียวกันเสมอ เช่น ftok(".", 'x')
  3. IPC_PRIVATEOS สร้าง key ไม่ซ้ำใครให้ — รับประกัน exclusive ใช้กันในพวกญาติ (parent/child, child/child) เพราะลูกได้ค่าสืบทอดตอน fork

💡 key เป็นชนิด key_t ตามที่กำหนดใน sys/types.h — ห้ามใช้ int/long แทน เพราะขนาดขึ้นกับระบบ

🎯 สรุปจุดออกสอบของ Shared Memory

• ลำดับ server: shmget → shmat → ใช้ → shmdt → shmctl(IPC_RMID) · client ไม่ทำ IPC_RMID!
• Client ที่ใช้ IPC_PRIVATE ต้องเป็นลูกที่เกิดหลังจากที่ parent ได้ shm มาแล้ว (ค่าผ่านทาง fork)
• Server ต้องเริ่มก่อน client เสมอ
• shmget สำเร็จคืน ID เป็นเลขไม่ลบ, ล้มเหลวคืนค่าลบ
