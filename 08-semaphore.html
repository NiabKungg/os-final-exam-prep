1. Semaphore คืออะไร + อุปมาโหลหิน 🪨

Semaphore S = ตัวแปร integer ที่เข้าถึงได้ผ่าน 2 คำสั่ง atomic เท่านั้น (ชื่อเดิม P/V จากภาษาดัตช์):

wait(S) {              // P = "ขอหิน"
    while (S <= 0);    // ไม่มีหิน → ยืนรอ
    S--;               // หยิบหินออกจากโหล 1 ลูก
}
signal(S) {            // V = "คืนหิน"
    S++;               // โยนหินกลับใส่โหล → ปลุกคนรอให้มาหยิบ
}
🪨 อุปมาโหลหินของอาจารย์

โหลใส่หิน = ทรัพยากรที่มีอยู่ (จำนวนหิน = ค่า S) · wait() = เดินมาหยิบหิน 1 ลูกถึงจะเข้าห้องน้ำได้ ถ้าโหลว่างต้องยืนรอ · signal() = ใช้เสร็จเอาหินมาคืนใส่โหล คนรอคนแรกจะได้หยิบต่อ

  • Counting semaphore — ค่าได้เลขเต็มใด ๆ ใช้กับทรัพยากรหลายชิ้น (มีห้องน้ำ 3 ห้อง = หิน 3 ลูก)
  • Binary semaphore — ค่าได้แค่ 0/1 เรียกอีกชื่อว่า mutex lock ใช้กันเข้า critical section ทีละคน

2. Implement แบบไม่มี Busy Waiting

เวอร์ชันด้านบน (while วนรอ) เป็น busy waiting — รอโดยเผา CPU เปล่า ปรับปรุงด้วย waiting queue: แต่ละ semaphore มีคิวของตัวเอง (แต่ละรายการเก็บ value + pointer รายการถัดไป)

wait(S) {
    S.value--;                    // หยิบหินก่อนเลย
    if (S.value < 0) {            // ติดลบ = หินไม่พอ มีคนรอแล้ว
        add ตัวเองเข้า S.list;     // ไปต่อคิว
        block();                  // หลับ — ไม่เผา CPU
    }
}
signal(S) {
    S.value++;                    // คืนหิน
    if (S.value <= 0) {           // ยังมีคนรออยู่
        remove P จาก S.list;
        wakeup(P);                // ปลุก 1 คนกลับ ready queue
    }
}

💡 ค่า value ติดลบ = มี process รออยู่เท่ากับ |value| ตัว (ออกถูก/ผิดได้)

3. ปัญหาที่ 1: Bounded Buffer (Producer-Consumer) 🔥🔥

Buffer n ช่อง ใช้ semaphore 3 ตัว — จำบทบาทให้แม่น เพราะข้อสอบชอบให้เติมชื่อ/ค่าเริ่มต้น:

Semaphoreค่าเริ่มต้นหน้าที่ (ในอุปมา)
mutex1ล็อก buffer — เข้าแตะของทีละคน (หิน 1 ลูก)
emptynนับ "ช่องว่าง" ที่เหลือ (หิน = สิทธิ์เขียน)
full0นับ "ช่องที่มีข้อมูล" (หิน = สิทธิ์อ่าน)

Producer (คนใส่ของ)

while (true) {
    // สร้าง item
    wait(empty);   // มีช่องว่างไหม? (หยิบหินจากโหล empty)
    wait(mutex);   // ล็อก buffer
    // เขียน item ลง buffer
    signal(mutex); // ปลดล็อก
    signal(full);  // คืนหินเข้าโหล full → บอก consumer ว่ามีของแล้ว
}

Consumer (คนหยิบของ)

while (true) {
    wait(full);    // มีของให้อ่านไหม?
    wait(mutex);
    // ดึง item ออกจาก buffer
    signal(mutex);
    signal(empty); // คืนหินเข้าโหล empty → มีช่องว่างแล้ว
    // ประมวลผล item
}
🚨 จุดหลอกยอดฮิต: สลับลำดับ wait → Deadlock!

ถ้า producer เขียนผิดเป็น wait(mutex); wait(empty); — ตอน buffer เต็ม producer จะได้mutex ไปครองก่อน แล้วไปติดรอ empty (จะว่างก็ต่อเมื่อ consumer อ่าน) แต่ consumer เข้ามาอ่านไม่ได้เพราะ mutex ถูก producer ครองค้าง! → รอกันตาย กฎเหล็ก: เช็คทรัพยากร (empty/full) ก่อน แล้วค่อยล็อก (mutex) เสมอ

4. ปัญหาที่ 2: Readers-Writers

ข้อมูลชุดหนึ่งถูกใช้โดย 2 พวก: Readers (อ่านอย่างเดียว) กับ Writers (อ่าน+เขียน) · กติกา: Reader หลายตัวอ่านพร้อมกันได้ แต่ Writer ทำงานเมื่อไร ห้ามใครยุ่งเด็ดขาด — ใช้ mutex = 1, wrt = 1, readcount = 0

Writer — ง่ายสุด

wait(wrt);
// เขียนข้อมูล
signal(wrt);

Reader — ใช้ readcount เป็น "ตัวแทนหมู่"

wait(mutex);              // ล็อกตัวนับ (แตะ readcount ทีละคน)
readcount++;
if (readcount == 1)      // reader ตัวแรกเป็นคนล็อก writer
    wait(wrt);
signal(mutex);
// อ่านข้อมูล (พร้อมกันได้หลายคน)
wait(mutex);
readcount--;
if (readcount == 0)      // reader ตัวสุดท้ายเป็นคนปลดล็อก
    signal(wrt);
signal(mutex);

💡 จำสั้น ๆ: "ตัวแรกล็อก ตัวสุดท้ายปลด" — ตัวกลาง ๆ เดินผ่านได้เลยเพราะผู้จัดการคือ readcount

5. ปัญหาที่ 3: Dining Philosophers (นักปราชญ์ 5 คน)

5 คน นั่งโต๊ะกลม กับข้าววางกลาง มี ตะเกียบ 5 อัน (อันละช่องว่างระหว่างคน) — จะกินข้าวได้ต้องมีตะเกียบครบ 2 ข้าง (ซ้าย+ขวา) ข้อมูลแชร์: semaphore chopstick[5] เริ่มทุกตัว = 1

โค้ดของนักปราชญ์ i
while (true) {
    wait(chopstick[i]);            // หยิบตะเกียบซ้าย
    wait(chopstick[(i + 1) % 5]);  // หยิบตะเกียบขวา
    // กินข้าว 🍚
    signal(chopstick[i]);          // วางซ้าย
    signal(chopstick[(i + 1) % 5]);// วางขวา
    // คิดปรัชญา 🤔
}
⚠️ จุดพังของโซลูชันนี้

ถ้า 5 คนหิวพร้อมกันและหยิบตะเกียบซ้ายได้ครบทุกคน → ไม่มีตะเกียบว่างเหลือเลย ทุกคนรอขวาเป็นวงกลม = Deadlock (ครบเงื่อนไข hold and wait + circular wait) — วิธีแก้คลาสสิก: จำกัดให้ 4 คนนั่งพร้อมกัน / หยิบพร้อมกันเท่านั้น / หรือใช้ Monitor (ข้างล่าง) ซึ่งกัน deadlock ได้ 100%

6. การใช้ Semaphore ผิดวิธี → เกิด Deadlock

Semaphore เป็นเครื่องมือระดับต่ำ OS ไม่ได้ตรวจว่าเราใช้ถูกไหม — ความผิดพลาดของโปรแกรมเมอร์ทำระบบพังได้:

ความผิดพลาดผลที่ตามมา
signal(mutex) … wait(mutex) (สลับที่)หลาย process อยู่ใน critical section พร้อมกัน (mutual exclusion แตก)
wait(mutex) … wait(mutex)Deadlock — ครอง lock แรกแล้วไปรอล็อกที่สอง
ลืม wait() หรือลืม signal()แย่งกัน / คนรอต่อคิวค้างตลอดไป
สอง process รอ semaphore สลับลำดับ (wait(S);wait(Q) กับ wait(Q);wait(S))Deadlock — ตัวอย่าง S/Q จากบท Deadlock (บท 9)

7. Monitor — ตัวเกราะระดับสูง

Monitor = abstraction ระดับสูง (คล้าย class ใน OOP) ที่รวม shared data + ฟังก์ชันจัดการไว้ด้วยกัน และรับประกัน mutual exclusion ให้อัตโนมัติ — ยอมให้มีเพียง 1 process อยู่ใน monitor ต่อ 1 เวลา นักเขียนโปรแกรมจึงลืมล็อก/ปลดล็อกไม่ได้ (ต่างจาก semaphore)

โครงสร้าง monitor
monitor monitor-name {
    // shared variable declarations
    procedure P1 (...) { ... }
    ...
    procedure Pn (...) { ... }
    initialization code (...) { ... }
}

จุดอ่อน: บางที process ที่อยู่ใน monitor ต้อง "รอเงื่อนไขอื่น" (เช่น รอเพื่อนบ้านเลิกกิน) — ถ้ารอในนั้นต่อ คนอื่นเข้าไม่ได้เลย จึงมี Condition Variables (x, y) มาช่วย:

  • x.wait() — process ที่เรียกจะหลับไปรอในคิวของเงื่อนไข x (ทำให้คนอื่นเข้า monitor ได้ต่อ)
  • x.signal() — ปลุก process รอใน x 1 ตัว · ข้อแตกต่างจาก semaphore สำคัญ: ถ้าไม่มีใคนรออยู่ สัญญาณจะหายไปเฉย ๆ (ไม่มี counter ให้เก็บยอด!)

แก้ Dining Philosophers ด้วย Monitor (กัน deadlock 100%)

monitor DP (จาก handout)
enum {THINKING, HUNGRY, EATING} state[5];
condition self[5];

void pickup(int i) {
    state[i] = HUNGRY;
    test(i);
    if (state[i] != EATING) self[i].wait;   // ยังหยิบไม่ได้ → หลับรอ
}
void putdown(int i) {
    state[i] = THINKING;
    test((i + 4) % 5);   // เช็คเพื่อนบ้านซ้าย
    test((i + 1) % 5);   // เช็คเพื่อนบ้านขวา
}
void test(int i) {       // กินได้เมื่อ "เพื่อนสองข้างไม่ได้กิน"
    if ( (state[(i + 4) % 5] != EATING) &&
         (state[i] == HUNGRY) &&
         (state[(i + 1) % 5] != EATING) ) {
        state[i] = EATING;
        self[i].signal();
    }
}

การใช้งาน: dp.pickup(i) → กิน → dp.putdown(i) — เพราะไม่มีใคร "ถือตะเกียบข้างเดียวค้างไว้" จึงไม่เกิด deadlock เลย (แต่ยังมีโอกาส starvation ถ้าเพื่อนบ้านสลับกันกินไม่เว้น!)

8. Java Synchronization

Java เอาแนวคิด monitor มาฝังในทุก object ผ่านคีย์เวิร์ด synchronized:

  • ทุก object มี lock ของตัวเอง — เรียก synchronized method ต้อง "เป็นเจ้าของ lock" ก่อน
  • Thread ที่มาตกคิวจะไปรอใน Entry Set · ออกจาก method = คืน lock อัตโนมัติ
  • wait() — ทำ 3 อย่าง: 1) คืน object lock 2) สถานะเป็น blocked 3) ย้ายเข้า Wait Set
  • notify() — สุ่มเลือก 1 thread จาก Wait Set ย้ายไป Entry Set (รอแย่ง lock ใหม่ — ไม่ได้รันทันที! และเลือกตัวเองไม่ได้)
  • notifyAll() — ปลุกทุกตัวใน Wait Set ขึ้นมาแย่งกันใน Entry Set — แนวรับที่ปลอดภัยกว่าเมื่อ wait set มีหลายตัว (ป้องกันเคส "ปลุกผิดตัวจนทุกคนรอกันตาย")
  • ตัวอย่างคลาสสิก: insert()/remove() ของ bounded buffer ด้วย while(count==...) wait(); ... notify(); (โค้ดเต็มใน handout)
  • Java 5+ มี java.util.concurrent.Semaphore จริง ๆ แล้ว: acquire() ≈ wait, release() ≈ signal
🎯 ตารางแยกพวก "wait" ที่หลอกเยอะที่สุด
wait ของใครทำอะไร
wait(S) ของ Semaphoreหยิบหิน — ลดค่า S, ไม่มีหินก็รอ
wait() ของ Java/Monitorสลัด lock + หลับใน Wait Set
wait() ของ Process (บท 3)Parent รอ Child จบ เก็บ exit status

แถม: Thread.yield() แค่ยอมออกจาก CPU ไปต่อคิว ready — ยังถือ lock ค้างอยู่ (เหมือนล็อกห้องแล้วปีนหน้าต่างหนี คนอื่นก็ยังเข้าไม่ได้!)
