บทที่ 12 — Virtual Memory: Demand Paging, การแทนที่เพจ และ Thrashing

Virtual memory ปลดล็อกกฎเหล็กของบทก่อน: โปรแกรมไม่ต้องอยู่ใน RAM ครบทั้งตัว! โหลดเฉพาะเพจที่กำลังใช้ (demand paging) — พอไม่พอดีก็มีอัลกอริทึมเลือก "ตัวปลอด" ออก ซึ่งเป็นแหล่งโจทย์นับ page fault ที่ออกทุกปี

1. Demand Paging — ขอเมื่อไร ค่อยเอามา

Virtual memory = การแยก logical memory ออกจาก physical memory ทำให้ address space ของโปรแกรมใหญ่กว่า RAM จริงก็ได้ · implement ได้ผ่าน demand paging หรือ demand segmentation

Demand paging = โหลดเพจเข้า RAM เฉพาะเมื่อถูกเรียกใช้ — หลัก "ขี้เกียจ" ของ lazy swapper (ตัวที่ทำงานกับเพจเรียกว่า pager) ผลลัพธ์: I/O น้อยลง, ใช้ RAM น้อยลง, ตอบสนองเร็วขึ้น, รองรับ user ได้มากขึ้น

Valid/Invalid bit ในบริบทใหม่

เพจที่ยังไม่ถูกโหลด → bit = i (invalid) — ตอนแปลง address เจอ i → เกิด Page Fault (trap เข้า OS) สังเกตว่า invalid ที่นี่ไม่ใช่ error ของโปรแกรมเสมอไป — ส่วนใหญ่แปลว่า "เพจนี้ยังไม่มา" ซึ่งเป็นเรื่องปกติของ demand paging

ขั้นตอนจัดการ Page Fault (6 ขั้น — เรียงลำดับได้ต้องได้คะแนน)

  1. Trap/Interrupt เข้าสู่ OSMMU เจอ valid–invalid bit = i → ยิง trap ไปยัง OS
  2. OS ตรวจว่า invalid แบบไหนดูตารางอ้างอิงอีกใบ: ถ้าอ้างผิดจริง ๆ (นอก address space) → abort process · ถ้าเป็นแค่"ยังไม่โหลด" → ไปขั้นต่อไป
  3. หาตำแหน่งเพจบนดิสก์แล้วหา frame ว่างใน RAM (ถ้าไม่มีว่าง → ใช้page replacement เลือกเพจอื่นออกก่อน — หัวข้อถัดไป)
  4. อ่านเพจจากดิสก์เข้า frame(ขั้นนี้แหละที่แพงที่สุด — เป็น I/O ทั้งตัว)
  5. อัปเดตตารางใส่ frame number + เปลี่ยน bit เป็น v
  6. Restart คำสั่งเดิมให้ CPU รัน instruction ที่พังอีกครั้ง — คราวนี้ใช้ได้ปกติ
⚠️ รายละเอียดปลีกย่อยที่ออกถูก/ผิด

เพจที่ถูกแก้ไขข้อมูล (dirty/modified bit = 1) ต้องเขียนกลับลงดิสก์ก่อน (write back) ค่อยแทนที่ — ไม่งั้นข้อมูลหาย · เพจที่ไม่ได้แก้ (clean) ทับได้เลยเพราะดิสก์มีสำเนาอยู่แล้ว

FIFO = 15 faults · Optimal = 9 faults · LRU = 12 faultsจำแนวเดียวกัน: ใน 3 อันนี้ Optimal น้อยสุดเสมอ (เพราะโกงรู้อนาคต) · LRU รองลงมา · FIFO มักแย่สุด

สรุปหลักคิดของแต่ละตัว

  • FIFO — ของที่เข้ามาก่อน ออกก่อน (ต่อคิวเฉย ๆ ไม่สนว่าใครฮิต) · ง่ายแต่โง่
  • Optimal (OPT) — เลือกแทนที่ตัวที่"จะไม่ถูกใช้อีกนานที่สุดในอนาคต" (มองไปข้างหน้า!) — ใช้จริงไม่ได้เพราะ OS รู้อนาคตไม่ได้ มีไว้เป็นเกณฑ์เทียบ (benchmark)
  • LRU — มองอดีต เลือกแทนตัวที่"ไม่ได้ใช้มานานที่สุด" — ทำจริงได้ (เก็บประวัติย้อนหลังได้) และดีกว่า FIFO
👕 เปรียบเทียบตู้เสื้อผ้า 3 ชั้น

FIFO = ชั้นล่างสุดคือของที่ใส่มานานสุด รีดออกก่อนไม่สนว่าจะใส่ซ้ำ · Optimal = หมอดูได้ รีดตัวที่จะไม่ใส่อีกนานสุด · LRU = จำได้ว่าเมื่อไรใส่ตัวไหนล่าสุด รีดตัวที่ทิ้งไว้นานสุด

3. Belady's Anomaly — เพิ่ม frame แล้ว fault กลับเพิ่ม?! 🤯

สามัญสำนึกบอกว่า RAM มากขึ้น = fault น้อยลง แต่ FIFO มีวันเสียสามัญสำนึก โจทย์คลาสสิก (จาก handout): reference string 1,2,3,4,1,2,5,1,2,3,4,5:

จำนวน frame3 frames4 frames
จำนวน page fault (FIFO)9 ครั้ง10 ครั้ง 😱

เพิ่ม frame หนึ่งช่อง fault กลับโตขึ้น — เรียกว่า Belady's Anomaly เกิดได้กับ FIFO (และอัลกอริทึมที่ไม่ใช่ stack algorithm) แต่ ไม่เกิดกับ LRU และ Optimal

4. EAT เมื่อมี Page Fault Rate (p)

เมื่อ p = อัตราการเกิด page fault (0 ≤ p ≤ 1):

EAT = (1 − p) × memory access time + p × page fault service timeขวาคือเวลาที่เจ็บปวดมาก เพราะรวม trap + I/O ดิสก์ + restart

ตัวเลขชวนคิด (มาตรฐานเท็กซ์บุ๊ก): ถ้า access = 200 ns แต่ page fault service = 8 ms → ที่ p = 1/1,000 (fault แค่ 0.1%) EAT = 0.999×200 + 0.001×8,000,000 ≈ 8,200 ns = 8.2 μs — ช้าขึ้นกว่า 40 เท่า! เพราะฉะนั้น "ห้ามให้ p โตเด็ดขาด" → โยงเข้าเรื่อง thrashing ข้างล่าง

5. Global vs Local Allocation

  • Global replacement — ตอนต้องแทนที่ เลือกเพจออกจาก frame ใดก็ได้ในระบบ (แย่งของข้าม process ได้)
  • Local replacement — เลือกจากเฉพาะ frame ของตัวเอง (คนละบ้านกับคนละบ้าน)

6. Thrashing, Locality of Reference และ Working Set 🔥

Thrashing — เครื่องยังเปิดแต่เหมือนตาย

  • ถ้า process มีเพจไม่พอ → fault ถี่มาก → วุ่นอยู่กับ สลับเพจเข้า-ออกดิสก์ตลอดเวลา (paging in/out ไม่หยุด)
  • ผล: CPU utilization ดิ่งเพราะ CPU หยุดรอดิสก์ตลอด
  • ความเข้าใจผิดอันตรายของ OS: เห็น CPU ว่าง ก็คิดว่า "งานน้อย เอา process เพิ่ม" → degree of multiprogramming สูงขึ้น → RAM ยิ่งแบ่งกันไม่พอ → thrashing ยิ่งหนักขึ้น (วงจรนรก)
  • เกิดได้ทั้งข้ามงาน (หลายงานแย่งเพจน้อย ๆ) และในงานเดียว (ลูปที่ข้ามขอบเพจไปมา)

Locality of Reference + Working Set — ยาแก้ thrashing

Locality of reference = พฤติกรรมธรรมชาติของโปรแกรม: ช่วงเวลาสั้น ๆ มักอ้างเฉพาะ "กลุ่มเพจเดิม ๆ" (เช่น อยู่ในฟังก์ชันเดียว วนลูปที่อาร์เรย์เดิม) — Working set = กลุ่มเพจที่ process ต้องใช้จริงใน locality นั้น (เก็บให้ครบใน RAM = ไม่มี fault ในช่วงนั้น)

  • Δ (working-set window) = จำนวนครั้งการอ้างที่ใช้มองย้อนหลัง (เช่น 10,000 instruction)
  • WSSᵢ = จำนวนเพจที่ Pᵢ อ้างใน window ล่าสุด · Δ เล็กไป = ครอบ locality ไม่หมด · Δ ใหญ่ไป = กินหลาย locality · Δ = ∞ คือทั้งโปรแกรม
  • D = Σ WSSᵢ = ความต้องการ frame รวมของระบบ · ถ้า D > m (จำนวน frame จริง) → thrashing! → OS ต้อง suspend บาง process (ส่งออกไปดิสก์) คืน frame ให้คนที่เหลือพอ
🍳 เปรียบเทียบ

Working set = "ของที่ต้องมีบนเคาน์เตอร์เพื่อทำเมนูนี้ให้จบ" ถ้าเคาน์เตอร์ (RAM) วางของไม่ครบ คุณจะวิ่งไปตู้เย็น (ดิสก์) ทุก 30 วินาที = ไม่มีอะไรเสร็จ (thrashing) ทางแก้คือลดจำนวน "เมนูที่ทำพร้อมกัน" (suspend process) ให้ของต่อเมนูพอ

7. โจทย์สุดคลาสสิก: Array 128×128 วนลูปสลับกัน 🔥

จากวิดีโอ 13.3 — int data[128][128] แต่ละ แถว (row) อยู่ใน 1 เพจ (เก็บแบบ row-major: ข้อมูลเรียงต่อกันตามแถว):

❌ แบบที่ 1: วน column นอก, row ใน (กระโดดข้ามแถวทุกครั้ง)

for (j = 0; j < 128; j++)       // column อยู่นอก
    for (i = 0; i < 128; i++)   // row อยู่ใน → ทุกการอ้างกระโดดเพจใหม่!
        data[i][j] = 0;

ทุกครั้งที่แตะสมาชิก 1 ตัว = เปลี่ยนเพจ = fault → 128 × 128 = 16,384 page faults

✅ แบบที่ 2: วน row นอก, column ใน (ไล่ต่อเนื่องในเพจเดียว)

for (i = 0; i < 128; i++)       // row อยู่นอก
    for (j = 0; j < 128; j++)   // column ใน → อยู่เพจเดียวกันทั้งแถว
        data[i][j] = 0;

เพจละ fault เดียวตอนเปลี่ยนแถว → 128 page faults เท่านั้น!

โค้ดเหมือนกัน แค่สลับลูป → fault ต่างกัน 128 เท่า (16,384 : 128)บทเรียน: เข้าใจ locality + โครงสร้าง memory ช่วยเขียนโค้ดเร็วขึ้นมหาศาล
