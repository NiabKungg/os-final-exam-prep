A. Process & การสร้าง Process ด้วย fork / exec / wait (OSNo03)

📖 รู้จักส่วนนี้ก่อนอ่าน

ความหมาย: Process = โปรแกรมที่ "มีชีวิต" กำลังทำงานอยู่ใน RAM มีสถานะและทรัพยากรของตัวเอง · fork = คำสั่งแตกสำเนา process (กระบวนการ), exec = เปลี่ยนโปรแกรมที่ process กำลังรัน, wait = ให้พ่อรอลูกจบ

ความสำคัญกับข้อสอบ: ข้อสอบชอบให้ "ไล่โค้ด fork" — นับว่ามี process เกิดกี่ตัว เดาว่า output พิมพ์อะไร รุ่นพี่เตือนว่ามีจุดหลอกเยอะ และย้ำว่าโค้ดทุกข้อ compile ผ่านหมด ไม่มีคำตอบว่า Error

ใช้จริงในคอมพิวเตอร์: ทุกครั้งที่พิมพ์คำสั่งใน terminal หรือดับเบิลคลิกเปิดแอป คือ shell (โปรแกรมรับคำสั่งผู้ใช้) ทำ fork → exec → wait ให้เราทั้งหมด — เช่น พิมพ์ ls, เปิด Chrome, compile ไฟล์

A3. fork() — สร้าง process แบบโคลนตัวเอง

pid_t fork(void) สร้าง child โดยก๊อปปี้ parent (address (ที่อยู่หน่วยความจำ) space, ตัวแปร, fd ทุกอย่าง) แล้วทั้งคู่รันต่อจากบรรทัดเดียวกัน (หลัง fork)

ใครเรียกค่าที่ fork() คืนเงื่อนไข if
ใน ParentPID ของลูก (> 0)if (pid > 0)
ใน Child0else if (pid == 0)
สร้างไม่สำเร็จค่าลบif (pid < 0) → error
🪄 เข้าใจง่าย

fork() เรียกครั้งเดียวแต่คืนค่า 2 ครั้ง — ครั้งนึงใน "โลกพ่อ" ครั้งนึงใน "โลกลูก" ทั้งคู่ถือ copy ของตัวแปร pid ของตัวเอง แก้ฝั่งไหนไม่กระทบอีกฝั่ง

/* fork_example.c — ตัวอย่างจากสไลด์/วิดีโอ: ผลลัพธ์พิมพ์ 2 บรรทัด */
#include <stdio.h>
#include <sys/types.h>   // pid_t
#include <unistd.h>      // fork()

int main(void) {
    pid_t pid;                    // เก็บค่า return ของ fork
    int i = 0;                    // ตัวแปรธรรมดา — จะถูก "ก๊อป" ไปให้ลูกด้วย

    pid = fork();                 // ← จุดแตกหน่อ: หลังบรรทัดนี้มี 2 process รันโค้ดชุดเดียวกัน
    if (pid > 0) {                // โลกพ่อ: ได้ PID ของลูก (>0) เสมอ
        i = 1;                    // แก้ i ใน address space ของพ่อ — ลูกไม่เห็น
        printf("I am parent i = %d\n", i);
    }
    else {                        // โลกลูก: fork คืน 0
        i = 2;
        printf("I am child i = %d\n", i);
    }
    return 0;
}

for (i = 0; i < 5; i++) {          // พ่อวน 5 รอบ
    pid = fork();

        if (i % 2 != 0) printf("I am happy\n");  // ลูกที่เกิดตอน i คี่

}
while (wait(NULL) != -1);            // พ่อรอลูกทุกตัว (wait คืน -1 เมื่อไม่มีลูกเหลือ)

A4. exec() — เปลี่ยนร่าง ไม่สร้างคนใหม่

  • ตระกูล exec แทนที่ process image ทั้งหมด (โค้ด+data) ด้วยโปรแกรมใหม่ — PID คงเดิม
  • execlp(file, arg0, arg1, ..., NULL) — l = list (ส่งทีละตัว) · p = หาโปรแกรมตาม PATH · arg0 = ธรรมเนียมใส่ชื่อโปรแกรม (exec ข้าม แต่ต้องใส่) · NULL ปิดท้ายบังคับ
  • execv: ส่งเป็น array char *argv[]
🎯 จุดหลอก exec

exec สำเร็จ → โค้ดหลังบรรทัด exec ไม่มีวันรัน (image โดนทับหมด) · exec ล้มเหลว (ชื่อผิด เช่น "ly") → รันบรรทัดถัดไปต่อ · exec("cd") fail เสมอเพราะ cd เป็น shell built-in ไม่ใช่ไฟล์ (echo ได้เพราะมี /usr/bin/echo)

A5. fork + exec + wait — รูปแบบมาตรฐานของ shell

int main() {
    pid_t pid = fork();
    if (pid < 0) {                          // สร้างลูกไม่สำเร็จ
        fprintf(stderr, "Fork Failed");
        exit(-1);
    }
    else if (pid == 0) {                    // ── ลูก: เปลี่ยนร่างเป็น ls ──
        execlp("/bin/ls", "ls", NULL);      // สำเร็จ = โค้ดลูกถูกแทนที่ทั้งหมด
    }
    else {                                  // ── พ่อ: รอลูก ──
        wait(NULL);                          // บล็อกรอลูกตัวใดตัวหนึ่งจบ (ได้ pid ลูกกลับ)
        printf("Child Complete");           // พิมพ์หลังลูกจบเสมอ
        exit(0);
    }
}

B. Thread & การเขียนโปรแกรม Multi-Threaded (OSNo04)

📖 รู้จักส่วนนี้ก่อนอ่าน

ความหมาย: Thread (เธรด/สายงานย่อย) = หน่วยทำงานที่เล็กกว่า process หลาย thread (เธรด (สายงานย่อย)) รันขนานกันภายใน process เดียวกันได้ โดยแชร์หน่วยความจำร่วมกัน

ความสำคัญกับข้อสอบ: ถามโมเดลการ map user thread (thread ฝั่งผู้ใช้) → kernel thread (Many-to-One / One-to-One / Many-to-Many) พร้อมตัวอย่าง OS, อ่านโค้ด Pthread/Java ว่าอะไรแชร์กัน และเชื่อมไปบท Synchronization (การประสานงาน)

ใช้จริงในคอมพิวเตอร์: เบราว์เซอร์ 1 แท็บใช้หลาย thread (โหลดหน้าเว็บ + เล่นวิดีโอ + รับการคลิก พร้อมกัน) · เกมออนไลน์ (เครือข่าย/กราฟิก/ฟิสิกส์แยกกัน) · Thread Pool (บ่อรวมเธรดเตรียมใช้งาน) ใช้ในเว็บเซิร์ฟเวอร์รับคำขอนับพันพร้อมกัน

B1. Thread คืออะไร

Thread = ลำดับคำสั่งที่รันได้อิสระภายใน process เดียวกัน (lightweight process) · สิ่งที่แต่ละ thread มีส่วนตัว: program counter, registers, stack · สิ่งที่แชร์กัน: code section, data section, heap, ไฟล์ที่เปิด — thread คือ "หน่วยที่ OS จัดคิวเข้า CPU" ในระบบสมัยใหม่ และสลับ thread ถูกกว่าสลับ process

int sum;  // ตัวแปร global — "แชร์" ระหว่าง thread (main กับ runner เห็นตัวเดียวกัน!)

/* ฟังก์ชันที่ thread จะรัน — signature ต้องเป็น void *f(void *) */
void *runner(void *param) {
    int upper = atoi(param);      // รับค่าจาก argv[1] ที่ส่งมาตอน create
    sum = 0;
    for (int i = 1; i <= upper; i++) sum += i;   // หาผลรวม 1..upper
    pthread_exit(NULL);            // จบ thread นี้ (≈ exit ของ process)
}

int main(int argc, char *argv[]) {
    pthread_t tid;                 // เก็บ id ของ thread ที่สร้าง
    pthread_attr_t attr;
    pthread_attr_init(&attr);      // ตั้งค่า attribute = default
    pthread_create(&tid, &attr, runner, argv[1]);
    //  ↑ สร้าง thread ให้รันฟังก์ชัน runner โดยส่ง argv[1] เป็น param
    pthread_join(tid, NULL);       // หลักของ main: รอ thread จบก่อน (≈ wait ของ process)
    printf("sum = %d\n", sum);     // เห็นค่า sum ที่ runner แก้ — เพราะแชร์กันจริง
}
/* จับคู่: pthread_create ≈ fork · pthread_join ≈ wait · pthread_exit ≈ exit */

C. CPU Scheduling — Gantt · TAT · WT (OSNo04 สไลด์ท้าย + วิดีโอ 6.x)

📖 รู้จักส่วนนี้ก่อนอ่าน

ความหมาย: CPU Scheduling = การตัดสินใจว่า process ไหนจะได้ใช้ CPU "ตัวต่อไป" เมื่อหลายงานแย่งกัน — มีหลายอัลกอริทึม เช่น FCFS (มาก่อนได้ก่อน), SJF (งานสั้นก่อน), RR (วนแบ่งเวลา)

ใช้จริงในคอมพิวเตอร์: Windows/Linux/macOS ใช้แนวคิด priority + time slice (โควตาเวลาแบบ RR) จริง ๆ ในตัวจัดคิวของเคอร์เนล — เปิด Task Manager เห็น process แย่ง CPU ด้วยกลไกพวกนี้ทั้งหมด

C1. พื้นฐาน + สูตรทุกตัวที่ใช้คิดเลข

  • CPU Scheduler (ตัวจัดคิว CPU) เลือก process จาก ready queue ให้ใช้ CPU · Non-preemptive = รันจนจบ/ขอออกเอง · Preemptive (ขัดจังหวะ/แย่งได้) = ขัดกลางคันได้ (หมดเวลา/มีตัวสำคัญกว่ามา)
  • CPU burst = ช่วงที่ process ใช้ CPU ติดกัน · I/O-bound = burst สั้นถี่ / CPU-bound = burst ยาว

D. Race Condition & Critical Section (OSNo06 ต้น ๆ)

📖 รู้จักส่วนนี้ก่อนอ่าน

ความหมาย: Race Condition = ปัญหาที่ 2 process แก้ข้อมูลแชร์พร้อมกันจนผลลัพธ์เพี้ยนตามใครแก้ก่อน-หลัง · Critical Section (ช่วงวิกฤต) = ช่วงโค้ดที่แตะข้อมูลแชร์ ห้ามใครเข้าพร้อมกัน

ความสำคัญกับข้อสอบ: ไล่ timeline การแย่งตัวแปร count (S0–S5), ท่องเงื่อนไข 3 ข้อ (Mutual Exclusion (เข้าถึงได้คนเดียว) / Progress / Bounded Waiting (รอได้จำกัดจำนวนครั้ง)), อธิบาย Peterson's Solution (โซลูชันสำหรับ 2 กระบวนการ) ว่าครบ 3 ข้อยังไง — ออกทั้งถูก/ผิดและไล่ค่า

ใช้จริงในคอมพิวเตอร์: ระบบธนาคารที่โอนเงินพร้อมกัน 2 คน, ตั๋วหนังที่นั่งสุดท้ายถูกซื้อพร้อมกัน, ตัวนับยอดวิว — ถ้าไม่ล็อก ข้อมูลเสียแบบใน timeline เลย

D1. จุดเริ่ม: Bounded Buffer (บัฟเฟอร์ขนาดจำกัด) ยังไม่มี sync (Producer (ฝั่งผู้ผลิตข้อมูล)-Consumer (ฝั่งผู้บริโภคข้อมูล))

Producer-Consumer แชร์ buffer วงแหวนขนาด BUFFER_SIZE ช่อง + ตัวนับ count — producer เขียนแล้ว count++ / consumer อ่านแล้ว count−−

/* Producer (สไลด์ p.3)                      Consumer (สไลด์ p.4) */
while (true) {                            while (true) {
    while (count == BUFFER_SIZE);            while (count == 0);   // busy wait
    buffer[in] = nextProduced;               nextConsumed = buffer[out];
    in = (in + 1) % BUFFER_SIZE;             out = (out + 1) % BUFFER_SIZE;
    count++;                                 count--;
}                                         }

D3. Critical Section — เงื่อนไข 3 ข้อที่โซลูชันต้องผ่าน 🔥

เงื่อนไขความหมาย (พิมพ์ได้ต้องได้)
1. Mutual Exclusionถ้า Pᵢ อยู่ใน CS (ช่วงวิกฤต) → ห้ามมี process อื่นอยู่ใน CS ของมันพร้อมกัน
2. Progressถ้าไม่มีใครอยู่ใน CS และมีคนอยากเข้า → ต้องเลือกจากคนที่อยากเข้าเท่านั้น และตัดสินไม่ล่าช้าไม่สิ้นสุด (กันคนไม่สนมาขวาง / กันไม่มีใครเข้าเลย)

โครงโค้ด: ENTRY SECTION → CRITICAL SECTION → EXIT SECTION → REMAINDER SECTION (วน while(true)) · สมมติ: แต่ละ process รันด้วยความเร็วไม่เป็นศูนย์ แต่ไม่มีข้อสมมติเรื่องความเร็วสัมพัทธ์

}

D5. Bakery Algorithm (n process) — จ่ายคิวร้านเบเกอรี่

  • ก่อนเข้า CS จ่ายเลขคิว = max(number[0..n−1]) + 1 → คนถือเลขน้อยสุดเข้าก่อน · เลขซ้ำเทียบ PID มาก่อนชนะ
  • เทียบแบบ lexicographical: (a,b) < (c,d) ถ้า a < c หรือ (a = c และ b < d) — (เลขคิว, pid)
  • แชร์: boolean choosing[n], int number[n] (เริ่ม false/0)
do {
    choosing[i] = true;                          // กำลังจ่ายเลข (ยังไม่นับคิวจริง)
    number[i] = max(number[0..n-1]) + 1;          // จ่ายเลขใหญ่กว่าใคร ๆ +1 (อาจซ้ำ)
    choosing[i] = false;
    for (j = 0; j < n; j++) {
        while (choosing[j]);                     // รอคนที่กำลังจ่ายเลขจบก่อน
        while ((number[j] != 0) && ((number[j],j) < (number[i],i)));
        // รอถ้า: เพื่อนถือคิวอยู่ และ (เลขน้อยกว่า หรือ เลขเท่าแต่ pid น้อยกว่า)
    }
    CRITICAL SECTION
    number[i] = 0;                               // ออก → ยกเลิกคิวตัวเอง
    REMAINDER SECTION
} while (true);

เลขคิวอาจกระโดด (1,2,3,3,3,4) — ไม่เป็นไร lexicographical จัดการเคสซ้ำ · รับประกันครบ 3 เงื่อนไขสำหรับ n process

📖 รู้จักส่วนนี้ก่อนอ่าน

ความหมาย: Semaphore (ตัวนับควบคุมคิว) = เครื่องมือที่ OS ให้มาจัดคิวเข้าถึงของแชร์อย่างปลอดภัย มีคำสั่ง wait (หยิบสิทธิ์) / signal (คืนสิทธิ์) · Monitor = กล่องควบคุมระดับสูงที่ล็อกให้อัตโนมัติ

ความสำคัญกับข้อสอบ: โค้ด Bounded Buffer / Readers-Writers (ปัญหาคนอ่าน-คนเขียน) / Dining Philosophers (ปัญหานักปราชญ์กินข้าว) ต้องจำค่าเริ่มต้นให้แม่น (mutex=1, empty=n, full=0) + จุดหลอก "สลับลำดับ wait → deadlock (การติดตาย (รอกันตลอดกาล))" — ออกถี่มาก

ใช้จริงในคอมพิวเตอร์: คิวงานเครื่องปรินต์, connection pool ของฐานข้อมูล, ปุ่ม like ที่คนกดพร้อมกันหลายพันคน — ระบบจริงทั้งหมดใช้ semaphore (ตัวนับควบคุมสิทธิ์เข้าถึง)/mutex คุมจังหวะ

E1. Semaphore — wait / signal (อุปมาโหลหิน 🪨)

wait(S) {              // P — "หยิบหินจากโหล"
    while (S <= 0);    // โหลว่าง → ยืนรอ (busy wait)
    S--;
}
signal(S) {            // V — "คืนหินใส่โหล" แล้วปลุกคนรอ
    S++;
}
  • Binary semaphore = ค่า 0/1 เท่านั้น อีกชื่อคือ mutex lock (การล็อก) → ใช้กับ critical section (เข้าได้ทีละคน)
  • Counting semaphore = ค่า 0..k → ใช้กับ resource (ทรัพยากร) หลายหน่วย (k = จำนวน resource)

E2. Implement แบบไม่มี busy waiting (waiting queue + block/wakeup)

/* แต่ละ semaphore มี waiting queue (แต่ละรายการเก็บ value + pointer รายการถัดไป) */
wait(S) {
    S.value--;                    // หยิบหินก่อนเลย
    if (S.value < 0) {            // ติดลบ = หินไม่พอ มีคนรอแล้ว
        เพิ่มตัวเองเข้า S.list;      // ต่อคิว
        block();                  // หลับ — ไม่เผา CPU
    }
}
signal(S) {
    S.value++;                    // คืนหิน
    if (S.value <= 0) {           // ยังมีคนรออยู่
        หยิบ P จาก S.list;
        wakeup(P);                // ปลุก 1 คนกลับ ready queue
    }
}
/* 💡 ค่า value ติดลบ = มี process รออยู่ |value| ตัว */

E4. ปัญหาคลาสสิก 2: Readers-Writers

กติกา: Reader หลายตัวอ่านพร้อมกันได้ · Writer ทำงานเมื่อไรห้ามใครยุ่งเด็ดขาด · แชร์: wrt=1, mutex=1, readcount=0 (int ธรรมดา)

/* Writer — ง่ายสุด */
wait(wrt);
// เขียนข้อมูล
signal(wrt);
/* Reader — "ตัวแรกล็อก ตัวสุดท้ายปลด" */
wait(mutex);              // แตะ readcount ทีละคน
readcount++;
if (readcount == 1)      // reader แรกล็อก writer
    wait(wrt);
signal(mutex);
// อ่านข้อมูล (พร้อมกันได้หลายคน)
wait(mutex);
readcount--;
if (readcount == 0)      // reader สุดท้ายปลดล็อก
    signal(wrt);
signal(mutex);

monitor DP {
    enum {THINKING, HUNGRY, EATING} state[5];   // สถานะของแต่ละคน
    condition self[5];                           // คิวรอของแต่ละคน

    void pickup(int i) {
        state[i] = HUNGRY;
        test(i);                                  // ลองดูว่ากินได้ไหม
        if (state[i] != EATING) self[i].wait;    // ยังไม่ได้ → หลับรอ
    }
    void putdown(int i) {
        state[i] = THINKING;
        test((i + 4) % 5);                       // เช็คเพื่อนบ้านซ้าย
        test((i + 1) % 5);                       // เช็คเพื่อนบ้านขวา
    }
    void test(int i) {
        // กินได้เมื่อ: เพื่อนซ้ายไม่กิน และ ฉันหิว และ เพื่อนขวาไม่กิน
        if ( (state[(i + 4) % 5] != EATING) &&
             (state[i] == HUNGRY) &&
             (state[(i + 1) % 5] != EATING) ) {
            state[i] = EATING;
            self[i].signal();
        }
    }
}
/* ใช้: dp.pickup(i) → EAT → dp.putdown(i)
   ไม่มีใคร "ถือตะเกียบเดี่ยวค้าง" → ไม่มี deadlock แน่นอน (แต่ starvation ยังเป็นไปได้) */

E7. Java Synchronization — synchronized (ล็อกอัตโนมัติ (คีย์เวิร์ด Java)) · wait · notify (ปลุก 1 thread ที่รออยู่)

  • ทุก object มี lock — เรียก synchronized method ต้องได้ lock ก่อน · ตกคิวไปรอใน Entry Set (คิวรอเข้าล็อก) · ออกจาก method = คืน lock อัตโนมัติ
  • wait() ทำ 3 อย่าง: (1) คืน object lock (2) สถานะ blocked (3) ย้ายเข้า Wait Set (คิวหลับรอเงื่อนไข)
  • notify() = สุ่ม 1 thread จาก Wait Set → ย้ายไป Entry Set (รอแย่ง lock ใหม่ — ไม่ได้รันทันที! และเลือกตัวเองไม่ได้) · notifyAll() = ปลุกทุกตัว (ปลอดภัยกว่าเมื่อ wait set มีหลายตัว)
  • Java 5+ มี Semaphore class จริง: acquire() ≈ wait, release() ≈ signal
/* insert() ด้วย wait/notify (สไลด์ p.41) */
public synchronized void insert(Object item) {

       try { wait(); }                  // เต็ม → คืนล็อก หลับรอ
       catch (InterruptedException e) { }
   }
   ++count;
   buffer[in] = item;
   in = (in + 1) % BUFFER_SIZE;
   notify();                            // ปลุกคนที่รออยู่ 1 ตัว
}
/* remove() (สไลด์ p.42) */
public synchronized Object remove() {
   Object item;
   while (count == 0) {
       try { wait(); }                  // ว่าง → หลับรอ
       catch (InterruptedException e) { }
   }
   --count;
   item = buffer[out];
   out = (out + 1) % BUFFER_SIZE;
   notify();
   return item;
}

F. Deadlock + Banker's Algorithm (OSNo07) 🔥

📖 รู้จักส่วนนี้ก่อนอ่าน

ความหมาย: Deadlock (การติดตาย) = กลุ่ม process รอทรัพยากรกันเป็นวงกลม ไม่มีใครได้ทำงานต่ออีกเลย · Banker's Algorithm = วิธี "เช็กก่อนให้" ว่าจัดสรรแล้วระบบยังปลอดภัยไหม

ความสำคัญกับข้อสอบ: เงื่อนไข 4 ข้อ (ต้องครบพร้อมกัน), อ่าน Resource-Allocation Graph (กราฟแสดงการจัดสรรทรัพยากร), และไล่ Safety Algorithm (อัลกอริทึม (ขั้นตอนวิธี)) หา Safe Sequence (ลำดับการรันที่ปลอดภัย) — เป็นแนวคำนวณหลักของ Final

ใช้จริงในคอมพิวเตอร์: ฐานข้อมูลล็อกแถวข้อมูล 2 ธุรกรรมรอกัน, เปิดไฟล์ Excel 2 โปรแกรมล็อกกัน, รถติด 4 แยกไม่มีใครยอมถอย — ระบบจริงเลือก "เมิน + ให้คนรีสตาร์ทเอง" เหมือนที่ OS ทำ

  • OS ส่วนใหญ่ (รวม UNIX) ไม่ป้องกัน/ไม่จัดการ deadlock เลย — ปล่อยให้โปรแกรมเมอร์รับผิดชอบ

F4.1 Avoidance แบบ single instance — Claim Edge (เส้นประ)

  • Claim edge Pᵢ ⇢ Rⱼ (เส้นประ) = "อาจขอในอนาคต" · ขอจริง → กลายเป็น request edge · ได้รับ → assignment edge · ปล่อย → กลับเป็น claim edge

  • ข้อเสีย: สแกนหา cycle ทุกครั้งที่ขอ = O(n²) แพง

F5. Banker's Algorithm (multiple instances) 🔥🔥

ข้อมูลที่ OS ถือ (n = process, m = resource type): Available[m] · Max[n×m] · Allocation[n×m] · Need = Max − Allocation

Need[i,j] = Max[i,j] − Allocation[i,j]หัวใจของทุกโจทย์ Banker's — คิด Need ให้ครบทุกช่องก่อนเสมอ

F5.1 Safety Algorithm (ตรวจว่า state ปลอดภัยไหม)

  1. Work = Available · Finish[i] = false ทุกตัว
  2. หา i ที่ Finish[i] = false และ Needᵢ ≤ Work (เทียบทีละช่องทุกชนิด) — ไม่มีใครผ่าน → ไปขั้น 4
  3. สมมติ i รันจนจบแล้วคืนของ: Work = Work + Allocationᵢ, Finish[i] = true → กลับขั้น 2
  4. ถ้า Finish = true ทุกตัว → SAFE (มี safe sequence) · ติดตรงไหน = UNSAFE

H. Paging & Address Translation (OSNo08 ท้าย) 🔥🔥

📖 รู้จักส่วนนี้ก่อนอ่าน — รีวิวรุ่นพี่: "คนส่วนมากคำนวณ Paging กันไม่ทัน"

ความหมาย: Paging (การแบ่งหน่วยความจำเป็นหน้าเท่า ๆ กัน) = หั่น RAM เป็น frame หั่นโปรแกรมเป็น page (ขนาดเท่ากัน) แล้วใช้ Page Table (ตารางจับคู่เพจ↔เฟรม) จับคู่ — "คำนวณ Paging" คือการแปลงที่อยู่ที่โปรแกรมเห็น (Logical) ให้เป็นที่อยู่จริงใน RAM (Physical)

ความสำคัญกับข้อสอบ: แปลง address ทีละบิต, TLB (แคชตารางเพจความเร็วสูง) + สูตร EAT (เวลาเข้าถึงเฉลี่ย), Two-level paging — เป็นแนวคำนวณที่ตัดสินว่า "ทันสอบหรือไม่ทัน" ต้องฝึกจนข้อละไม่เกิน 1 นาที

ใช้จริงในคอมพิวเตอร์: CPU ทุกตัวสมัยใหม่ (x86, ARM ในมือถือ) + OS ทุกตัว (Windows/Linux/macOS/Android) ใช้ paging จริง 100% — แอปแต่ละตัวเห็น "RAM ของตัวเอง" ก็เพราะกลไกนี้

H1. แนวคิด Paging

  • Paging = จัดสรรแบบ non-contiguous (ไม่ต้องติดกัน) — ตัด external fragmentation ขาด
  • Frame (เฟรม (ก้อน RAM)): แบ่ง RAM เป็นบล็อกขนาดคงที่ ขนาดเป็นกำลังสอง 2ⁿ bytes (512–8,192)
  • Page (หน้า): แบ่งโปรแกรมเป็นบล็อกขนาดเท่า frame เป๊ะ · รันโปรแกรม n เพจ = หา frame ว่าง n อันกระจายวาง
  • Page table: จับคู่ "เพจ i → frame ไหน" ของแต่ละ process
🎯 เช็คความเข้าใจ

Paging ไม่มี External frag แต่มี Internal frag — เกิดเฉพาะเพจสุดท้ายถ้าขนาดโปรแกรมไม่ลงตัว

Hashed Page Table — สำหรับ address space ใหญ่มาก

เมื่อ address space กว้างมาก (64-bit) ตารางเพจแบบลำดับชั้นจะลึกเกินไป จึงใช้ฟังก์ชัน hash ของ page number ไปชี้ entry ในตาราง แล้วเดินตามห่วงโซ่ (chain) ของ element ที่ hash ชนกัน จนเจอแถวที่ page number ตรง แล้วอ่าน frame number — ดีกับเพจที่กระจายตัว ไม่ต้องสร้างตารางครบทุกช่อง

Inverted Page Table — 1 แถวต่อ 1 frame จริง

ปกติตารางเพจมี 1 แถวต่อ 1 เพจเสมือน ของ process (สร้างหลายตาราง) แต่ Inverted กลับด้าน: 1 แถวต่อ 1 frame จริงใน RAM เก็บ (pid, page) ที่ครอบอยู่ — มีตารางเดียวสำหรับทั้งระบบ ประหยัด RAM มาก · ราคาที่จ่าย: ตอนแปลง address ต้องค้นหา (pid, page) ของตัวเองทั้งตาราง → ช้า จึงต้องมี hash table + TLB ช่วย

หมายเหตุ: ทั้งสองแบบเป็นแนวทางแก้ปัญหา "page table ใหญ่เกิน" ร่วมกับ Two-level ที่เจอข้างบน — ข้อสอบมักถามรู้จักชื่อ + หลักคิดสั้น ๆ แบบนี้พอ

I. Virtual Memory & Page Replacement (OSNo09) 🔥🔥

📖 รู้จักส่วนนี้ก่อนอ่าน

ความหมาย: Virtual Memory (หน่วยความจำเสมือน) = โปรแกรมไม่ต้องอยู่ใน RAM ครบทั้งตัว โหลดเฉพาะเพจที่กำลังใช้ (demand paging) ทำให้ RAM จริงเหมือนใหญ่กว่าจริง · Page Replacement = เมื่อ RAM เต็ม ต้องเลือกเพจ "ตัวปลอด" ออก

ความสำคัญกับข้อสอบ: นับ page fault (เพจยังไม่อยู่ใน RAM) ทั้ง FIFO (เข้าก่อน-ออกก่อน) / Optimal (ดีที่สุดเชิงทฤษฎี) / LRU (รู้ผล 15/9/12 ของ string หลัก), Belady's Anomaly (ปรากฏการณ์เพิ่ม RAM แล้ว fault เพิ่ม), Thrashing (สลับเพจหนักจนระบบแย่) — เป็นแนวคำนวณหลักอีกแนวของ Final

ใช้จริงในคอมพิวเตอร์: เปิดเกมใหญ่กว่า RAM เครื่องได้, สลับแอปเร็วโดยไม่โหลดใหม่, ขนาด "หน่วยความจำเสมือน" ที่เห็นใน Task Manager คือกลไกนี้ — ข้อมูลที่ไม่ได้ใช้ถูกส่งไปพักบน disk

I1. Demand Paging (โหลดเพจเฉพาะเมื่อถูกใช้) — ขอเมื่อไรค่อยเอามา

  • Virtual memory = แยก logical memory ออกจาก physical → address space ใหญ่กว่า RAM จริงก็ได้ · implement ผ่าน demand paging หรือ demand segmentation
  • Demand paging: โหลดเพจเฉพาะเมื่อถูกเรียกใช้ — หลักขี้เกียจของ lazy swapper (ตัวทำงานกับเพจเรียก pager) · ผลดี: I/O น้อย, RAM น้อย, ตอบเร็ว, รองรับ user มาก
  • เพจที่ยังไม่โหลด → bit = i (invalid) → แปลง address เจอ i → Page Fault (เพจยังไม่อยู่ใน RAM) — invalid ที่นี่ส่วนใหญ่ไม่ใช่ error แค่ "ยังไม่มา"

I5. EAT เมื่อมี Page Fault Rate (p)

EAT = (1 − p) × memory access time + p × page fault service timeตัวเลขชวนคิด: mat = 200ns, fault service = 8ms → ที่ p = 0.001 (fault แค่ 0.1%) EAT = 0.999×200 + 0.001×8,000,000 ≈ 8,200ns = 8.2μs — ช้าขึ้น 40 เท่า! ห้ามให้ p โต

I6. Global vs Local Allocation

  • Global replacement: แทนที่ได้จาก frame ใดก็ได้ในระบบ — แย่งข้าม process ได้
  • Local replacement: เลือกจากเฉพาะ frame ของตัวเอง (คนละบ้านกับคนละบ้าน)

I7. Thrashing · Locality · Working Set (ชุดเพจที่ต้องมีใน RAM) 🔥

  • Thrashing: process มีเพจไม่พอ → สลับเพจเข้า-ออก disk ตลอดเวลา → CPU utilization ดิ่ง · OS เข้าใจผิดว่า "งานน้อย" เลยเพิ่ม process → thrashing (สลับเพจหนักจนระบบแย่) ยิ่งหนัก (วงจรนรก) · เกิดทั้งข้ามงานและในงานเดียว (ลูปข้ามเพจ)
  • Locality of reference: โปรแกรมมักอ้างกลุ่มเพจเดิมซ้ำ ๆ ในช่วงสั้น ๆ (อยู่ในฟังก์ชัน/ลูปเดิม)
  • Working set: กลุ่มเพจที่ process ต้องมีใน RAM เพื่อไม่ให้ fault ในช่วง locality นั้น — มองย้อนหลัง Δ (working-set window เช่น 10,000 instruction) · WSSᵢ = จำนวนเพจที่ Pᵢ อ้างใน Δ · Δ เล็กไปครอบ locality ไม่หมด / ใหญ่ไปกินหลาย locality / Δ = ∞ คือทั้งโปรแกรม
  • D = Σ WSSᵢ = ความต้องการ frame รวม · ถ้า D > m (frame จริง) → thrashing! → OS ต้อง suspend บาง process คืน frame ให้คนที่เหลือ
