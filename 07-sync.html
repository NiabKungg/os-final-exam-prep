บทที่ 7 — Race Condition และ Critical Section

เมื่อหลาย process แชร์ข้อมูลกัน (แบบ shared memory จากบทที่ 6) เวลาเกิด "ชนกัน" ข้อมูลจะพัง บทนี้จะพาไล่ให้เห็นว่ามันพังยังไง (แบบที่อาจารย์ไล่ในวิดีโอ) แล้วพูดถึงเงื่อนไขที่โซลูชันต้องทำได้ 3 ข้อ พร้อมโซลูชันซอฟต์แวร์คลาสสิก 2 ตัว

1. จุดเริ่มต้น: Bounded Buffer ที่ยังไม่มีการจัดจังหวะ

Producer-Consumer แชร์ buffer ขนาดจำกัด (BUFFER_SIZE ช่อง) และตัวนับ count — producer เขียนแล้ว count++, consumer อ่านแล้ว count-- (โค้ดเต็มอยู่ใน handout: ใช้วงแหวน modulo แบบ in = (in + 1) % BUFFER_SIZE)

โค้ดดิบ ๆ ที่ยังพังอยู่
// Producer                                // Consumer
while (true) {                             while (true) {
    while (count == BUFFER_SIZE);              while (count == 0); // รอว่าง
    buffer[in] = nextProduced;                 nextConsumed = buffer[out];
    in = (in + 1) % BUFFER_SIZE;               out = (out + 1) % BUFFER_SIZE;
    count++;                                   count--;
}                                          }

ปัญหา: producer อาจเขียนทับข้อมูลที่ยังไม่ถูกอ่าน, consumer อ่านช่องเดิมซ้ำ — และหัวใจของบทคือ count++/count-- ไม่ใช่คำสั่งเดียว!

2. Race Condition — ไล่ timeline ให้เห็นกับตา 🔥

ในระดับภาษาเครื่อง count++ แตกเป็น 3 คำสั่ง:

/* count++ เทียบเท่ากับ: */       /* count-- เทียบเท่ากับ: */
register1 = count;                 register2 = count;
register1 = register1 + 1;         register2 = register2 - 1;
count = register1;                 count = register2;

เมื่อสอง process รันพร้อมกัน OS สลับใช้ CPU ได้ทุกจังหวะ (interleaving) — นี่คือตัวอย่างจากวิดีโอ เริ่มที่ count = 5:

💳 เปรียบเทียบ

เหมือนเงินในบัญชี 5,000 บาท คุณโอนเข้า +1,000 ส่วนแฟนถอนออก −1,000 พร้อมกัน แต่แอปเด้งให้ทั้งคู่เห็นยอด "5,000" พร้อมกันแล้วบันทึกทับกัน สุดท้ายบัญชีเหลือ 4,000 — เงินหายไปในอากาศ!

📖 นิยามที่ต้องพิมพ์ได้

Race Condition: สถานการณ์ที่ process หลายตัวเข้าถึงและจัดการข้อมูลร่วมกันพร้อม ๆ แล้วผลลัพธ์สุดท้ายขึ้นอยู่กับลำดับการเข้าถึง (ทำให้ผลลัพธ์ "อาจถูกอาจผิด") — โค้ดที่แตะข้อมูลแชร์ช่วงนี้คือ critical section

3. Critical Section Problem — เงื่อนไขที่โซลูชันต้องผ่าน 3 ข้อ 🔥

Critical section (critical region) = ส่วนของโค้ดที่แตะทรัพยากรแชร์ ต้อง "จบให้คนเดียว" ก่อนถึงมีคนอื่นเข้าได้ โครงของทุก process:

while (true) {
    /* ENTRY SECTION — ขอสิทธิ์เข้า */
    CRITICAL SECTION   // แตะข้อมูลแชร์ตรงนี้
    /* EXIT SECTION — คืนสิทธิ์ */
    REMAINDER SECTION  // งานส่วนที่ไม่แตะข้อมูลแชร์
}

โซลูชันที่ดีต้องทำ 3 เงื่อนไขนี้ได้ (ออกเรียงข้อ/จับผิดข้อความบ่อยมาก):

  1. Mutual Exclusionถ้า Pi อยู่ใน critical section ห้ามมี process อื่นอยู่ใน critical section ของมันพร้อมกัน (ทีละคนเด็ดขาด)
  2. Progressถ้าไม่มีใครอยู่ใน critical section และมีคนอยากเข้า → ต้องเลือกคนเข้าจากคนที่อยากเข้าเท่านั้น และการเลือกตัดสินไม่ได้ล่าช้าไม่มีที่สิ้นสุด (กันเคส "คนที่ไม่สนใจมาขวางเสียเปล่า" และเคส "ไม่มีใครเข้าไปเลย")
  3. Bounded Waitingมีขอบเขตว่า process หนึ่งจะถูก "ตัดหน้า" ได้จำกัดกี่ครั้งหลังจากยื่นขอเข้า (กัน starvation ของการรอคิว critical section)

ข้อสมมติ: แต่ละ process รันด้วยความเร็วไม่เป็นศูนย์ แต่ไม่มีข้อสมมติเรื่องความเร็วสัมพัทธ์ระหว่าง process

4. Peterson's Solution — โซลูชัน 2 process

แชร์ 2 ตัวแปร: int turn (ตาใคร) และ boolean flag[2] (ใครพร้อมจะเข้า) — ข้อสมมติ: LOAD/STORE เป็น atomic (ห้ามถูกขัดกลางคำสั่ง)

โค้ดของ Pᵢ (อีกฝั่งคือ Pⱼ)
while (true) {
    flag[i] = TRUE;          // บอกว่า "ฉันอยากเข้า!"
    turn = j;                // ยกมือให้เพื่อนไปก่อน (ความสุภาพคือหัวใจ)
    while (flag[j] && turn == j);  // รอเฉพาะเมื่อ: เพื่อนอยากเข้า "และ" ถึงตาเพื่อน

    CRITICAL SECTION

    flag[i] = FALSE;         // เดินออก → ปล่อยให้คนอื่นเข้าได้
    REMAINDER SECTION
}
  • Mutual exclusion ✓ — ใครตั้ง turn เป็นฝ่ายอื่นเป็นคนสุดท้าย ต้องรอก่อน (ทั้งคู่ตั้งพร้อมกันไม่ได้)
  • Progress ✓ — เงื่อนไขรอต้องเจอ flag[j] จริง ๆ (คนที่ไม่สนใจเข้าไม่ขวาง)
  • Bounded waiting ✓ — หลังออกจาก CS, turn จะยกให้อีกฝั่งเสมอ อีกฝั่งได้เข้าภายใน 1 รอบ
📌 ความจริงในโลกปัจจุบัน

Peterson เวิร์คในทฤษฎี แต่บน CPU สมัยใหม่ที่มี compiler optimization / out-of-order execution อาจพัง — ที่ใช้จริงเราใช้ฮาร์ดแวร์/ไลบรารี (ตัวอย่าง: Semaphore ในบทถัดไป) แต่ Peterson เป็นข้อสอบยอดนิยมเพราะสอนหลักคิดได้ดี

5. Bakery Algorithm — กระจายไป n process

อุปมา: ร้านเบเกอรี่จ่ายเลขคิว — คนถือเลขน้อยสุดได้เข้าก่อน เลขเท่ากันดู PID มาก่อนชนะ (เทียบแบบ lexicographical: (เลขคิว, pid))

โครงโค้ด (แชร์: choosing[n], number[n] เริ่ม false กับ 0)
do {
    choosing[i] = true;                       // กำลังจ่ายคิว ยังไม่นับเป็นคิวจริง
    number[i] = max(number[0], ..., number[n-1]) + 1;  // จ่ายเลขใหญ่กว่าใคร ๆ +1
    choosing[i] = false;                      // เลขออกแล้ว เข้าสู่คิวจริง

    for (j = 0; j < n; j++) {
        while (choosing[j]);                  // รอคนที่กำลังจ่ายเลขจนจบก่อน
        while ((number[j] != 0) &&
               ((number[j], j) < (number[i], i))); // ใครเลขน้อยกว่า/เลขเท่าแต่ pid น้อยกว่า ได้ก่อน
    }
    CRITICAL SECTION
    number[i] = 0;                            // เดินออก → ยกเลิกคิวตัวเอง
    REMAINDER SECTION
} while (true);
⚠️ จุดสังเกตสำหรับข้อสอบ

• เลขคิวอาจ "กระโดด" (1, 2, 3, 3, 3, 4) ไม่เป็นระเบียบ — ไม่เป็นไร เทียบแบบ lexicographical ช่วยจัดการเคสเลขซ้ำ
• ระหว่างจ่ายเลข (choosing = true) ตัวเองยัง "ไม่มีสิทธิ์ขวางใคร" — รอบประกัน progress
• Bakery รับประกันครบทั้ง 3 เงื่อนไข สำหรับ n process

✏️ข้อ 2เติมตัวเลข — ไล่ timeline จากวิดีโอ

S0: producer r1 = count (r1=5) · S1: r1 = r1+1 (r1=6) · S2: consumer r2 = count (r2=5) · S3: r2 = r2−1 (r2=4) · S4: producer count = r1 · S5: consumer count = r2
ค่าสุดท้ายของ count คือเท่าไร
เฉลย: 4เพราะ consumer เขียนทับเป็นคนสุดท้าย (S5) ด้วย r2 = 4 — ทั้งที่ตามตรรกะ +1 แล้ว −1 ควรได้ 5 นี่คือพลังทำลายล้างของ race condition
🔤ข้อ 3ปรนัย
เงื่อนไข Progress ของ critical section problem กล่าวว่าอย่างไร
กทุก process ต้องได้เข้า critical section พร้อมกันเพื่อความเร็ว
ขprocess ที่อยู่ใน critical section ต้องจบภายในเวลาที่กำหนด
คถ้าไม่มีใครอยู่ใน critical section และมี process อยากเข้า ต้องเลือกจาก process ที่อยากเข้าเท่านั้น และตัดสินไม่ได้ล่าช้าไม่สิ้นสุด
งprocess ที่รอนานที่สุดต้องได้เข้าเสมอ
