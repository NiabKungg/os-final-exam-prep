1. พื้นฐานและสูตรที่ต้องท่องขึ้นใจ

CPU Scheduler = ตัวเลือกว่า process ไหนใน Ready queue จะได้ใช้ CPU ตัวต่อไป แบ่ง 2 นิสัยใหญ่ ๆ:

  • Non-preemptive — ให้ใช้แล้วใช้จนเสร็จ/ขอออกเอง ไม่มีใครชิงได้
  • Preemptive — OS ขัดกลางคันได้ (หมดเวลา, มีงานสำคัญกว่ามาแย่ง)

เกณฑ์วัดว่าอัลกอริทึมไหนดี: ให้ CPU ทำงานเต็มเปี่ยม (max CPU utilization), ทำงานเสร็จเยอะ (max throughput), และลด 3 เวลานี้ — turnaround, waiting, response

Turnaround Time (TAT) = Completion Time − Arrival Timeเวลารวมตั้งแต่งานมาถึงระบบจนเสร็จ
Waiting Time (WT) = Turnaround Time − Burst Timeเวลาที่นั่งเปล่าใน Ready queue — เทคนิคอาจารย์: คิด TAT ก่อนแล้วลบ BT เสมอ โดยเฉพาะงาน preemptive ที่งานโดนแทรกหลายรอบ!
💡 ทำไมต้องใช้ WT = TAT − BT (ไม่ไล่นับจาก Gantt)

ในอัลกอริทึม preemptive งานหนึ่งโดนแทรกหลายรอบ ถ้าไล่นับช่วงรอจาก Gantt ทีละช่วง มักนับเกิน/ขาด — แต่ถามว่า "งานอยู่ในระบบนานเท่าไร (TAT)" กับ "มันใช้ CPU จริงเท่าไร (BT)" ง่ายกว่ามาก เอามาลบกัน = เวลาเหลือที่ไม่ได้ใช้ CPU = เวลารอ แม่นและเร็วกว่าเสมอ

SJF คือ optimal — ให้ค่าเฉลี่ย waiting time ต่ำที่สุดจากชุดงานหนึ่ง ๆ แต่ใช้จริงยาก เพราะ OS รู้ทันไหมว่างานจะกิน CPU นานแค่ไหน (ต้อง "ทำนาย" ความยาว CPU burst ถัดไป)

4. SRTF — Shortest Remaining Time First (Preemptive SJF) 🔥

กติกา: ทุกครั้งที่มีงานใหม่มาถึง เทียบ "เวลาที่เหลือ" ของงานที่รันอยู่ กับ Burst ของงานใหม่ — ถ้างานใหม่สั้นกว่า จะขัดทันที ใช้ข้อมูลเดิม:

  1. เวลา 0–2P1 รันไป 2 หน่วย (เหลือ 5) — จู่ ๆ P2 มาถึง (BT=4)
  2. เวลา 2 — เทียบ!เหลือของ P1 = 5 vs P2 = 4 → P2 สั้นกว่า → ขัด P1 → รัน P2
  3. เวลา 4P2 รันไป 2 (เหลือ 2) — P3 มาถึง (BT=1) → 1 < 2 → ขัด P2 → รัน P3
  4. เวลา 5P3 เสร็จพอดี + P4 มาถึง (BT=4) คิวตอนนี้: P1(5), P2(2), P4(4) → สั้นสุด P2(2) → รันจนจบที่ 7
  5. เวลา 7เหลือ P1(5), P4(4) → รัน P4 จบที่ 11 → แล้ว P1 รันเศษ 5 จบที่ 16

5. Priority Scheduling

แต่ละงานมีเลขสิทธิ ให้ CPU กับงานสิทธิสูงสุดก่อน (มีแบบ preemptive และ non-preemptive) จุดที่โดนหลอกบ่อยคือทิศทางของเลข:

Unix-based: เลขน้อย = สิทธิสูง Java Thread: เลขมาก (สูงสุด 10) = สิทธิสูง
  • ปัญหา: Starvation (อดตาย) — งานสิทธิต่ำอาจไม่ได้รันเลยเพราะมีงานสิทธิสูงแทรกไม่หยุด
  • วิธีแก้: Aging — ยิ่งรอนาน ยิ่งเพิ่ม priority ให้ จนถึงเวลาหนึ่งก็ได้รัน
  • มุมมองหนึ่ง: SJF ก็คือ priority scheduling ที่ใช้ "predicted next CPU burst" เป็น priority

6. Round Robin (RR) — Preemptive, เน้นตอบสนองไว

ให้แต่ละงานรันไม่เกิน Time Quantum (q) (มัก 10–100 ms) หมดเวลายังไม่เสร็จ → ถูกขัดแล้วไปต่อท้ายคิว · โจทย์วิดีโอ (ข้อมูลเดียวกับ FCFS, q = 4):

  1. เวลา 0–4P1 รันได้ 4 (เหลือ 20) โดนตัด → ไปต่อคิว
  2. เวลา 4–7P2 ต้องการแค่ 3 (น้อยกว่า q) → รันจนเสร็จ
  3. เวลา 7–10P3 เช่นกัน เสร็จที่ 10
  4. เวลา 10–30เหลือ P1 ตัวเดียว รันรอบละ 4 จนครบ 24 → จบที่ 30

ข้อสังเกตจาก handout: ถ้าคิวมี n งานกับ quantum q จะไม่มีงานรอเกิน (n−1)·q หน่วยเวลา

⚖️ ขนาด quantum สำคัญกับ Overhead

q ใหญ่มาก → RR กลายเป็น FCFS · q เล็กมาก → context switch ถี่เกิน overhead บานปลาย (เสียเวลาสลับงานมากกว่าทำงานจริง) — จำเชื่อมกับบท 3: ช่วง context switch คือ overhead ที่ไม่ได้ทำงานมีประโยชน์เลย

7. Multilevel Queue และ Multilevel Feedback Queue (MLFQ)

  • Multilevel Queue — แยก Ready queue เป็นหลายคิว เช่น foreground ใช้ RR / background ใช้ FCFS แต่งานอยู่คิวไหน = อยู่ตลอดชีวิต ย้ายไม่ได้ ระหว่างคิวจัดลำดับแบบ fixed priority (คิวหน้าจบก่อนคิวหลัง — เสี่ยง starvation) หรือแบ่งเวลา (เช่น 80% foreground, 20% background)
  • MLFQ — เพิ่มความยืดหยุ่น: งานย้ายข้ามคิวได้ ใช้ทำ aging หรือจัดกลุ่มตามพฤติกรรม

โมเดลตัวอย่างในวิดีโอ (3 คิว):

  1. Q₀: RR ที่ quantum 8 msงานใหม่เข้าที่นี่ก่อนเสมอ ทำไม่เสร็จใน 8 ms → ถูกเทลง Q₁
  2. Q₁: RR ที่ quantum 16 msได้เวลาเพิ่มอีก 16 ms ยังไม่เสร็จอีก → เทลง Q₂
  3. Q₂: FCFSรันจนเสร็จ แต่ Q₂ จะได้รันก็ต่อเมื่อ Q₀ กับ Q₁ ว่างหมดแล้ว
🏥 เปรียบเทียบ

เหมือน รพ. — ผู้ป่วยใหม่เข้าห้องฉุกเฉิน (Q₀) โดนตรวจย่อ 8 นาที ถ้าเรื่องยาวมากจะโดนย้ายไปคลินิกพิเศษ (Q₁) อีก 16 นาที สุดท้ายถ้ายังไม่จบไปรอทำตามคิวปกติ (Q₂) แต่ถ้าเคสฉุกเฉิน (Q₀) เข้ามาใหม่เมื่อไร ได้สิทธิ์ก่อนเสมอ

8. Java Thread Scheduling

  • Java spec ไม่ fix มาตรฐาน — ขึ้นกับ JVM แต่ทั่วไปคือ preemptive + priority-based
  • Priority 1–10, default 5, ตั้งด้วย setPriority(); ตัวสูงกว่าได้เลือกก่อน, ระดับเดียวกันสุ่มเลือก
  • รันจนกว่า: มีตัว priority สูงกว่ามา / yield() / run() จบ / หมด time-slice
  • อย่าฝาก correctness ไว้กับ scheduler! ต้องใช้ Synchronization ควบคุมเอง

9. สรุป 5 จุดพลาด (จากเน้นของอาจารย์ในวิดีโอ)

  1. ลบ Arrival Time ไม่ครบ — เอาเวลาเริ่มรันจาก Gantt ตอบเป็น WT ทันที (ถูกต้อง: ใช้ WT = TAT − BT)
  2. WT ใน preemptive นับช่วงรอไม่ครบ — งานโดนแทรกหลายรอบ ไล่นับมือพลาดง่าย → ใช้สูตร TAT − BT เสมอ
  3. ตีความ priority ผิดฝั่ง — Unix เลขน้อย = สูง / Java เลขมาก = สูง
  4. SRTF ลืมหัก Remaining Time — ต้องใช้เวลาที่เหลือเทียบ ไม่ใช่ burst ดั้งเดิม
  5. เลือก quantum ผิด — ใหญ่ไปกลายเป็น FCFS เล็กไป overhead โต
