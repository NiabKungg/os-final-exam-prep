บทที่ 9 — Deadlock: จากสะพานตัน สู่ Banker's Algorithm

Deadlock คือสถานการณ์ที่ process ตั้งแต่ 2 ตัวขึ้นไปรอกันเป็นวงกลมไม่รู้จบ — ในวิดีโออาจารย์ใช้ตัวอย่างสะพานแคบเลนเดียว และได้บอกในคลิป 11.5 ว่าขอข้าม Banker's Algorithm เพราะนอกสโคป (แต่มีเต็ม ๆ ใน handout และเป็นแนวโจทย์คำนวณสวย ๆ เราจึงสอนครบไว้ให้)

1. เงื่อนไข 4 ข้อ — ต้องเกิด "พร้อมกัน" จึงเกิด Deadlock

ตัวอย่างรากฐานจากวิดีโอ: โค้ดนี้เกิด deadlock ได้ (S, Q เป็น binary semaphore เริ่ม 1 ทั้งคู่):

/* P0 */              /* P1 */
wait(S);              wait(Q);
wait(Q);              wait(S);
...                   ...
signal(S);            signal(Q);
signal(Q);            signal(S);

ถ้า P0 ยึด S แล้วถูกสลับออก → P1 ยึด Q → P0 รอ Q (ที่ P1 ถือ) / P1 รอ S (ที่ P0 ถือ) — ตายล็อก! นี่คือ Circular Wait และเพื่อให้เกิดได้ต้องมีครบทั้ง 4 เงื่อนไข:

  1. Mutual Exclusion (ใช้ร่วมกันไม่ได้)ทรัพยากร 1 ชิ้น มีได้ 1 เจ้าของในแต่ละเวลา (เช่น S, Q ที่เป็น binary semaphore)
  2. Hold and Wait (ถือเก่า รอใหม่)process ถือทรัพยากรอย่างน้อย 1 ชิ้นไว้ แล้วรอชิ้นอื่นที่คนอื่นถืออยู่ (P0 ถือ S รอ Q)
  3. No Preemption (ยึดกลางคันไม่ได้)ทรัพยากรจะปล่อยได้เมื่อเจ้าของใจดีปล่อยเองเท่านั้น — ไม่มีใครมาแย่งได้
  4. Circular Wait (รอเป็นวง)มีชุด {P₀, P₁, …, Pₙ} ที่ P₀ รอของ P₁, P₁ รอของ P₂, …, Pₙ วนกลับมารอของ P₀
🎯 จำแน่น ๆ

เงื่อนไขต้องเกิด ครบทั้ง 4 พร้อมกัน จึงเกิด deadlock — ตัดได้เพียงข้อเดียวก็ไม่เกิด (หลักการของ Deadlock Prevention) และเชื่อมจากบท 8: Dining Philosophers หยิบซ้ายพร้อมกัน = ครบ 4 ข้อพอดี

2. Resource-Allocation Graph (RAG)

  • วงกลม = Process (Pi) · สี่เหลี่ยม = Resource type (Rj) โดยจุดในสี่เหลี่ยม = จำนวนชิ้น (instances)
  • Request edge Pi → Rj : Pi กำลังขอใช้
  • Assignment edge Rj → Pi : ทรัพยากรถูกให้ Pi ถืออยู่
ไม่มี cycle → ไม่เกิด deadlock แน่นอน (100%)
มี cycle → ทรัพยากรชิ้นเดียวต่อประเภท = deadlock แน่ · หลายชิ้น = "อาจเกิด"สองบรรทัดนี้คือข้อสอบถูก/ผิดยอดนิยม

3. 4 กลยุทธ์จัดการ Deadlock

  1. Prevention (ป้องกันเด็ดขาด)ออกแบบให้เงื่อนไขใดเงื่อนไขหนึ่งเกิดไม่ได้เลย — ดูรายละเอียดด้านล่าง
  2. Avoidance (หลีกเลี่ยง)ยอมให้มีเงื่อนไข แต่ให้ processแจ้ง Max ที่จะใช้ล่วงหน้า OS ตรวจทุกครั้งก่อนจัดสรรว่ายังเป็น safe state ไหม (Banker's)
  3. Detection + Recovery (ยอมให้เกิด แล้วตามจับ)ปล่อยเกิด สแกนหา deadlock ระยะ ๆ แล้วจัดการแก้
  4. เมิน (Ostrich)OS ส่วนใหญ่รวมถึง UNIX เลือกวิธีนี้! — ทำเหมือนไม่มีอะไรเกิดขึ้น ให้โปรแกรมเมอร์จัดการเอง

Prevention — ตัดทีละเงื่อนไข

เงื่อนไขที่ตัดวิธีผลข้างเคียง
Mutual Exclusionทำให้ทรัพยากรแชร์กันได้ทำไม่ได้กับทุกชนิด (บางอย่างธรรมชาติต้องใช้ทีละตัว)
Hold and Waitขอและได้ครบทุกชิ้นก่อนเริ่มรัน หรือ อนุญาตให้ขอเมื่อไม่ถืออะไรเลยใช้ทรัพยากรไม่คุ้ม (จอง printer ค้างไว้ทั้งที่ยังไม่พิมพ์) + starvation ได้
No Preemptionขอเพิ่มไม่ได้ = ถูกยึดทรัพยากรที่ถืออยู่ทั้งหมดคืน เอาไปให้คนที่รออยู่ แล้วค่อยเริ่มใหม่เมื่อได้ครบยุ่งยาก สถานะงานค้าง starvation ได้
Circular Waitให้ทุกทรัพยากรมีเลขประจำตัว และขอเรียงจากเลขน้อยไปมากเท่านั้น เช่น Disk = 4, Printer = 11 → ต้องได้ 4 ก่อน 11 ห้ามถือ 11 แล้วขอ 4ลำดับเลขไม่อาจเหมาะกับทุกโปรแกรม
📌 ข้อสรุปของอาจารย์

Prevention ทำได้ในทฤษฎีทุกข้อ แต่ทางปฏิบัติเสียประสิทธิภาพหนักมาก OS จึงไม่ค่อยเลือกใช้ — ข้อนี้เคยถามเป็นถูก/ผิด

4. Banker's Algorithm — ไล่ตารางจาก Handout ทีละขั้น 🔥

📌 หมายเหตุจากวิดีโอ

ในคลิป 11.5 อาจารย์กล่าวถึง Banker's สั้น ๆ แล้วบอกว่าขอข้าม (นอกสโคปวิชา) แต่เนื้อหาเต็มอยู่ใน Handout No.7 และมันคือแนวคำนวณแบบข้อสอบพอดี — แนะนำให้ทำได้ ไม่เสียหาย

ใช้กับทรัพยากรหลายชิ้นต่อประเภท ข้อมูลที่ OS ถือ (n = จำนวน process, m = จำนวน resource type):

  • Available[m] — ของว่างแต่ละชนิด
  • Max[n×m] — ขอสูงสุดที่ประกาศไว้ · Allocation[n×m] — ที่ถืออยู่ตอนนี้
  • Need[n×m] = Max − Allocation — ที่อาจยังขออีก

ไล่ Safety Algorithm (เริ่ม Work = Available = (3,3,2))

หา process ที่ Finish[i] = false และ Needᵢ ≤ Work → ถ้าเจอ: สมมติให้รันจนเสร็จแล้วคืนของ Work = Work + Allocationᵢ ทำซ้ำจนหมด = SAFE (ถ้าตันกลางทาง = UNSAFE)

  1. เลือก P1 (Need 1,2,2 ≤ Work 3,3,2 ✓)P1 รันจบคืนของ → Work = (3,3,2)+(2,0,0) = (5,3,2)
  2. เลือก P3 (Need 0,1,1 ≤ 5,3,2 ✓)คืนของ → Work = (5,3,2)+(2,1,1) = (7,4,3)
  3. เลือก P4 (Need 4,3,1 ≤ 7,4,3 ✓)คืนของ → Work = (7,4,3)+(0,0,2) = (7,4,5)
  4. เลือก P2 (Need 6,0,0 ≤ 7,4,5 ✓)คืนของ → Work = (7,4,5)+(3,0,2) = (10,4,7)
  5. เลือก P0 (Need 7,4,3 ≤ 10,4,7 ✓)คืนของ → Work = (10,5,7) — Finish ครบทุกตัว ✅
Safe sequence หนึ่งคือ <P1, P3, P4, P2, P0> → ระบบอยู่ใน SAFE STATEsafe sequence อาจมีหลายคำตอบ — ตอบคำใดที่ตรวจแล้วผ่านก็ถูก แต่ต้องเขียนเหตุผล Work ที่เปลี่ยนไปทีละขั้น

ถ้า P1 ขอเพิ่ม (1,0,2) — ให้ได้ไหม? (Resource-Request Algorithm)

  1. ตรวจ Request ≤ Need(1,0,2) ≤ (1,2,2) ✓ ผ่าน (ไม่ใช่การขอเกินที่ประกาศไว้)
  2. ตรวจ Request ≤ Available(1,0,2) ≤ (3,3,2) ✓ ผ่าน (ของพอ)
  3. สมมติจัดให้ (pretend)Available = (2,3,0) · P1 Allocation = (3,0,2) · P1 Need = (0,2,0)
  4. รัน Safety Algorithm ใหม่ไล่ได้ sequence <P1, P3, P4, P0, P2> → ยัง safe ✅
  5. สรุปให้ไปได้! (ถ้าไล่แล้ว unsafe → ไม่ให้ ให้ P รอ และคืนสถานะเดิม)

แบบฝึกหัดเดียวกันใน handout ยังถามต่อ: P4 ขอ (3,3,0)? → ตอบ "ไม่ได้" เพราะของว่าง (ตอนนั้น = 2,3,0) ไม่พอ · P0 ขอ (0,2,0)? → ผ่านสองเช็คแรก แต่ไล่ safety แล้วunsafe → ไม่ให้

5. Detection (ตรวจจับ) & Recovery (กู้)

Detection

  • ทรัพยากรชิ้นเดียวต่อประเภท — ยุบ RAG เป็น Wait-For Graph: ตัดโหนดทรัพยากรออกหมด เหลือเส้น Pi → Pj ตรง ๆ ("Pi รอ Pj") แล้วสแกนหา cycle (เรียกทุก ๆ ระยะ, แพงระดับ O(n²))
  • หลายชิ้นต่อประเภท — Detection Algorithm ทำงานเหมือน Safety แต่เทียบด้วย Request (ของที่ร้องขอค้างอยู่จริง) แทน Need

Recovery

  • Process Termination — จบทุกตัวที่ติด (แน่แต่เสียงานหมด) หรือจบทีละตัวจนวงแตก (เลือกจาก: priority, รันไปแล้วนานแค่ไหน, ใช้ทรัพยากรอะไรไปแล้ว, ต้องการอีกเท่าไร, จบกี่ตัวถึงพอ, เป็น interactive/batch?)
  • Resource Preemption — เลือกเหยื่อ (victim), rollback ไป safe state แล้วเริ่มใหม่ · ระวัง starvation ถ้าตัวเดิมถูกเลือกเป็นเหยื่อซ้ำ ๆ → ใส่ "จำนวนครั้งที่โดน rollback" ไว้ในตัวแปรต้นทุนด้วย
